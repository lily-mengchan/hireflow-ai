# Mock 数据层与本地持久化

## 统一模型

- **Job**：岗位与流程模板，不持久化 applicants/hired 等可派生统计。
- **Candidate**：唯一 ID 的模拟档案，不携带某个岗位的招聘阶段。
- **Application**：连接 candidateId 与 jobId，拥有独立 ID、阶段、处理状态、面试状态和预置匹配分。同一候选人与同一岗位只允许一份申请；不同岗位分别记录。
- **InterviewRecord**：按 applicationId 关联，记录阶段、时间、面试状态及备注。完成已安排面试时保留其原时间，流转事件额外保留修改前后状态。
- **RecruitmentEvent**：追加写入的岗位和申请事件，包括申请 ID、岗位/候选人 ID、发生时间、说明和状态 before/after。

复用现有 UI 的联合类型 CandidateApplication 只是读模型；所有进度更新命令都必须传 applicationId，不能按 candidateId 批量覆盖申请。

初始化提供 6 个岗位、16 位虚构候选人、17 份申请、多阶段流转与面试记录。同一位模拟候选人的两份申请用于演示独立进度。重置时重新生成相对于当前日期的演示时间，便于观察最近 7 天趋势。

## 数据访问

页面调用 useRecruitment 订阅共享状态，调用 recruitmentActions 执行保存或重置。localStorage 访问集中在数据层，存储键为 `hireflow-ai:recruitment:v1`，整个数据快照包含 version=1。

React useSyncExternalStore 使用稳定的服务端初始快照；只在客户端开始订阅时读取浏览器存储，避免 SSR 访问 window 和 hydration 数据不一致。初次访问无存储键时初始化并保存。其他同源标签页的 storage 事件会重新读取该键。

Repository 每次命令读取最新持久化快照，执行校验、更新、追加事件，完成整份快照写入后才发布给页面。浏览器禁止存储、空间不足等错误会显示为保存失败，不会提示成功。损坏 JSON、未知版本或无效外键不会被静默覆盖；顶部显示提示，用户可明确重置。

已有申请的岗位禁止直接切换流程模板，以免旧招聘阶段失效。新岗位或没有申请的岗位仍可选择流程模板。模板变化需后续实现显式迁移流程。

localStorage 不提供多标签页事务锁；正常依次操作会读取最新快照，完全同时写入时采用最后写入者的快照。该实现用于单用户前端 Demo，不承担多用户协作与跨设备同步。

## 统计口径

- 候选人数：Candidate 档案总数，按唯一 ID 计数。
- 岗位数：共享状态内全部岗位数，包含暂停和结束状态。
- 待安排面试：未淘汰、非 Offer、面试状态为待安排的申请，再按候选人 ID 去重。
- Offer：当前 Offer 阶段且未淘汰的申请数；当前状态回退或淘汰会更新此数值。
- 岗位候选人数：该岗位的申请数；已录用为 Offer 阶段且处理状态为已通过的申请数。
- 漏斗：每份申请按当前阶段及事件中的历史阶段，统计曾达到各阶段的人次。包含淘汰及回退的历史，设计岗位的作品集评审与业务复筛归为同一层级。
- 趋势：按 Asia/Shanghai 自然日计算的最近 7 天或前 7 天候选人创建数和面试记录数。
- 最近动态：按发生时间倒序展示共享 RecruitmentEvent，不使用固定招聘动态文案。

## 验证

`npm run test:data` 使用 Node 内置测试运行器和现有 TypeScript 编译器，无新增测试依赖。测试采用内存 StorageAdapter，模拟刷新后重新创建 Repository，覆盖存储恢复、岗位编辑、独立申请、历史事件、统计联动、面试记录、重置、损坏数据和写入失败。

页面的创建、更新进度和重置仍需在浏览器操作时具备 localStorage 权限。无数据库、API、真实 AI、上传服务或原 AI-Hire 代码修改。
